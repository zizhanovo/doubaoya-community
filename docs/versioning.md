# 版本号：两个数，答两个不同的问题

每个包同时带两个「版本」，**它们不是同一个东西，不许合并**：

| | 在哪 | 谁写 | 回答什么 |
|---|---|---|---|
| **内容哈希** | `skills/<slug>/.version` | 机器算（提交钩子自动） | 是不是**同一份东西** —— 更新提示的判据 |
| **语义版本** | `SKILL.md` frontmatter `version:` | **人写** | 这次改了什么、**会不会弄坏我** |

合并任一个，就失去另一个能回答的问题：
哈希永远说不出「这是破坏性变更」；semver 是人写的、**会烂**。

## 枢纽：哈希逼 semver 说实话

> **内容哈希变了 ⇒ semver 必须也变，且严格递增。**

由 `tools/tests/test_semver.py` 强制。哈希是派生的、不会骗人，
所以它能当 semver 的诚实性保证。

🔴 **诚实边界**：闸只能强制「**变了**」，**判不出 major / minor / patch 选得对不对**。
那是你的判断，下面这张表是依据。

## 该进哪一档

| 档 | 什么情况 | 判据 |
|---|---|---|
| **patch** `x.y.Z` | 措辞、错别字、补例子 | **行为不变**，老用法照样成立 |
| **minor** `x.Y.0` | 新增能力、新增 reference、行为变化但向后兼容 | 老用法**仍然成立** |
| **major** `X.0.0` | 改名、删能力、红线变更、契约变更 | 老用法**会坏** |

拿不准就问一句：**照旧那么用的人会不会坏？** 会坏就是 major。

## 真实例子（2026-08-22）

- `dby-publish` **1.4.0 → 2.0.0**：流水线 md→HTML 改走平台渲染，`:::` 组件语法退场。
  照旧写 `:::关注卡` 的人会看到那几个字符原样出现在正文里 ⇒ **会坏 ⇒ major**。
- 其余 6 个包首次声明 → **1.0.0**。首次声明**没有历史可破坏**，
  即使近期有破坏性提交也从 1.0.0 起（`dby-image` 就是这种）。

## 为什么不另起一个 meta 文件

查过三家，**没有一家是「每包一个 meta.json」**：

- **Agent Skills 规范**：必填只 `name`/`description`；`version` 不是标准字段，
  「spec-compliant runtimes ignore 不认识的键」
- **ClawHub**：就读 `SKILL.md` frontmatter，官方例子逐字 `version: 1.2.0`
- **腾讯 SkillHub**：集中式索引；它的 `metadata.json` 是 **CLI 工具自己的**元数据
  （`~/.skillhub/metadata.json`，唯一被读的字段是 `self_update_manifest_url`），
  不是每包一份

另外**哈希也不该塞进 frontmatter**：`.version` 现在能工作，正是因为哈希算法
**整个排除了那一个文件**；混进 `SKILL.md` 会自引用，还要引入 YAML 规范化 ——
键序 / 缩进 / 引号 / 转义任一变化都会改哈希，**全体存量用户一次性收到假更新提示**。

## 改了版本号会怎样

`SKILL.md` 变了 ⇒ **内容哈希也变** ⇒ 已装该包的用户会收到一次「有更新」。
这是正常的，也是**对的**：他们确实该知道版本变了。

⚠️ 但别为了「避免哈希变」而把 version 挪到不参与哈希的地方 ——
那等于让版本号变化对更新提示不可见，用户升级后拿不到新版本号，
又回到「提示不消失」那条循环。
