# 交付回执：格式与硬性规则

> 每次交付都随手带一份；回执随交付写，不事后补。模式 A 第 3 步、模式 B 第 6 步要写回执时读它。

## 终态

`dby` 不问终态；终态（成稿 / 排版 HTML / 进草稿箱）由 `dby-write` 成稿后问，终态门以 `dby-api/references/wechat-routing.json` 为准。
**目标停在哪一档，就在哪一档收手**：用户只要成稿时不跑 `dby-publish`（它会写进用户自己的公众号后台）；
用户要进草稿箱却停在成稿才是断头。用户已说的终态照走，别替他决定。

## 格式

交付末尾附上，四种状态**分开写**：

```
查阅：<读了哪份路由 / 导航图>
执行：<真正跑了哪些 skill>
质检：<跑了哪些检查>
跳过：<发现了但没跑的 skill> —— 原因：<为什么不该跑>
```

## 硬性规则

- **四行别合并。**「执行」只写**真的跑过**的；没跑的一律不许出现在这一行。
- **「跳过」区分两件事**：*压根没发现* 的不必列；**发现了、但判断不该跑** 的**必须**列并写明原因。
  带副作用的（`dby-publish` 会写进用户自己的公众号后台）尤其不能省。
- **如实**：跑了但失败的写在「执行」并注明，不许挪进「跳过」粉饰；没做质检就写「无」。
- **回执里只许写能证明的量。** 结论必须回指某个**真实返回的字段**（违禁词检测的
  `prohibitedWordsType` 是类别数组，「命中 N 类」可证；接口**不回**等级 / 评分 / 命中词清单，
  「0 高危」「低风险」就是编的）。拿不准是不是真字段，就别写这个量。
- 四行以内。

## 例子（用户要的终态是「只要成稿」）

```
查阅：dby 路由表 → 写作链
执行：dby-api（拉爆文样本）、dby-write（写正文）
质检：dby-banned-words（命中 2 类，已按标注调整相关表述）
跳过：dby-publish —— 你这次只要 Markdown 成稿；它会把文章写进你自己的公众号
      草稿箱，要排版好的 HTML 或要进草稿箱再说一声，我接着跑。
```
