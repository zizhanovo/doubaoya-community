# 模式 C：按审稿意见改一版

> 用户说「按审稿意见改一版 / 按我的评论再改一遍 / 读一下稿件 xxx 的意见」时读它。
> 写一篇（模式 A）、复盘一篇（模式 B）不需要读。

这是稿件面（`dby-api` 的 `draft` 系列命令，字段与错误码见 `references/api-contract.md` 的「稿件面」一节）上的第三种交互：
用户已经在审稿页留了评论、拒绝了几处 agent 改动，这一轮的活是**逐条回应**，不是重写整篇。

## 四步

```bash
D=~/.claude/skills/dby-api/scripts/doubaoya.mjs
```

### 0. 先拿到稿件 id（拿不到就问，不许猜）

用户话术（「按审稿意见改一版」「按我的评论再改一遍」）多半不带 id。按这个顺序取：

1. 用户消息里带了稿件 id 或审稿页链接 → 直接用（链接里的那段 id）。
2. 本会话早些时候 `draft create` / `draft submit` 返回过 id、或交棒 `dby-publish --draft <id>` 用过 → 用它，
   并向用户复述一句「按稿件 <id>《标题》的意见改」，让他有机会纠正。
3. 都没有 → 停下问：「要改哪一篇？把审稿页里的稿件 id 或链接发我。」
   🔴 `draft` 系列**没有 list 子命令**，本包拿不到「待审稿件清单」——别编一个不存在的命令去列，
   也别拿 `write.mjs articles`（已发文章）顶替，那是另一张表。

### 1. 拉审稿包（唯一的读入口）

```bash
node "$D" draft review-packet <稿件id>
```

一次拿齐：`head`（最新版正文与版本号）、`comments[]`（全部待处理评论）、`rejections[]`（自上次
本包写入之后用户新做出的拒绝，含被拒改动的原文 / 替换 / 理由 / 用户备注）、`stars[]`（星标与说明）。
**别再调别的端点**——这是设计上刻意的单一入口（漏读一处的代价，往期同类问题见 `materials.md` 的教训）。

`comments[]`、`rejections[]` 都空 → 如实告诉用户「没有待处理的意见」，不产生新版本，到此为止。

### 2. 逐条回应

对 `comments[]` 每一条、`rejections[]` 每一条：

- **能改** → 在 `head.bodyMd` 里定位这条意见对应的原文，组一条 `changes[]`：
  `anchor.exact` 摘录 `head` 里的原文，`replacement` 是改完的说法，`reason` 写「回应评论 #<id>」或
  「回应第 <version> 版被拒的第 <changeId> 处」，`tag` 按 `dby-rewrite` 同一条纪律——有名的技法才填，没有留空。
  这条评论的 id 记进待提交的 `addresses[]`（评论）；拒绝没有 `addresses` 机制，改完即视为回应了，
  不需要额外标记。
- **不能改**（意见有道理但这版不适合改 / 意见有歧义 / 意见与红线冲突）→ **不强行造一条改动**，
  改成在评论下回复说明为什么这版没动它：
  ```bash
  node "$D" draft comment <稿件id> '{"parentId":"<评论id>","body":"<为什么没改>","author":"dby-write"}'
  ```
  拒绝没有对话线程可回复——处置方式是在这版的摘要里带一句「关于第 x 处拒绝：<为什么坚持/或已按原文保留>」。

逐条过，**别挑轻松的改、把难的漏掉**——审稿包给的就是全部待办，处理完的数量要能对上「查阅」里读到的数量。

### 3. 提交新版

```bash
node "$D" draft submit <稿件id> '{"baseVersion":<head.version>,"author":"dby-write","addresses":["<已回应的评论id>",...],"changes":[...]}'
```

`baseVersion` 用第 1 步 `head.version`（审稿包读的就是当前最新版，两次调用之间没有人抢先提交的话
基准版本就是它；`submit` 若报 409 `VERSION_CONFLICT` 说明确实有人抢先了，按 `api-contract.md` 的处置
重拉 `review-packet` 再来一轮）。`changes[]` 为空但 `addresses` 非空（全部意见都是"不能改"的回复处理）
时不提交新版，只发评论回复——正文没变，提交空 `changes[]` 只会撞 422 `NO_DIFF`。

### 4. 回报

按本包交付回执的格式，额外带一句量化小结：

> 处理了 N 条评论、回应了 M 处拒绝（其中 K 条改了正文、其余在评论 / 摘要里说明了原因），
> 第 x 版已生成。

**红线四仍适用**：这版仍是改写产物，交给用户看过再问是否需要继续（终态问法与模式 A 相同）。

## 与模式 A 的取材边界

模式 C 改的是「已成文的这一版」，不是重新走一遍第 4 步收素材——但如果某条评论要求的内容在
素材单之外（用户在评论里给了新事实），这条新事实本身要能指回来源（红线一同样适用），
不能凭空编一句应付评论。
