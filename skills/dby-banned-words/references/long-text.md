# 长文案：2000 字上限、自动分段与结果合并

> 只在文案**超过 2000 字**（整篇公众号文章、长笔记）时才需要读这份。≤2000 字时 CLI 一段打完，
> 结果形状与本节无关，照 SKILL.md 主体的契约读即可。

## 上游的硬上限

上游单次只能收 **2000 字**，超了必定报错——所以**别自己截断、也别把整篇硬塞**，CLI 已经替你分段：

- 超过 2000 字时自动切成多段，每段 ≤2000 字，切点优先落在**段落**、其次**句末标点**
  （一整段没有任何标点又超长才会硬切）。分段**无损**：各段拼回来与原文一字不差。
- **计费 = 平台数 × 段数**：3000 字的文案查三个平台 = 6 次调用。确认态的 `changes` 会逐段列出
  （`违禁词检测 · xiaohongshu（第 1/2 段，2000 字）`），核对的就是这个次数。
- 结果自动**合并成一个平台条目**，你不用自己拼：`content` / `originalContent` 是全文的
  标注版与原文，`prohibitedWordsType` 是各段类别的并集，`segments` 里逐段给
  `{ index, chars, prohibitedWordsType }` —— 命中落在第几段看这里。
- 有段落失败时，该平台条目会同时带 `error`（`BANNED_SEGMENT_FAILED`）、
  `content` / `originalContent` 为 `null`，并在 `segments[].error` 里指出是哪几段。
  🔴 **这时绝不能当成通过**：只扫了一半的文案没有合规结论，照 SKILL.md
  [「没拿到结果」](SKILL.md#每个平台怎么判有没有命中)那一档处理，并把错误文案里那句
  `只覆盖 N/M 段` 如实转达给用户。

## 怎么调用

```bash
# 长文整篇给，不用自己截断：CLI 按段落 / 句末标点自动分段。
# 3000 字查一个平台 = 2 段 = 2 次计费；确认态会把每一段各列一条。
dby banned check "$(cat article.md)" --platforms gongzhonghao --confirm
```

## 自己拼请求时（不走 CLI）

`content` 单次**最多 2000 字**（上游硬上限，服务端在扣点前就 400 拒掉）。自己拼请求必须按这个数
分段：超过它不会「查得少一点」，而是**整段拿不到结果**。分段时优先切在段落与句末标点上，
别做重叠窗口——重叠会让同一个命中在相邻两段各报一次，段数还照翻倍计费。

## 上游「成功但正文为空」

上游偶尔（实测约 600 次里 2 次）回一个**成功信封**，正文却是空的：
`{content: null, originalContent: null, prohibitedWordsType: []}`。

🔴 这**不是「零命中」**——零命中的形状是拿到了正文、且 `content` 与 `originalContent` 相等。
CLI 把它记成 `UPSTREAM_EMPTY`，等于「这一段没查」，与段失败同样处理（该平台条目回到
「没拿到结果」那一档，不许写成「未命中」/「合规」）。原样重试一次通常就有结果。

## 上游的内容风控

另有第三类拒绝，与长度无关：正文里带脚本 / SQL 注入特征（`<script>`、引号、`--`、`select` 之类）
时上游会回 `body.content 参数包含不合法内容，请移除脚本或SQL注入特征字符后重试`。
这是**换一段文本**才有用，重试同一段没用——写代码教程、贴 SQL / 报错日志的文案会撞上它。

## 错误处理

CLI 逐平台、逐段捕获网络 / HTTP 错误，把错误写进对应条目并继续其它平台与其它段：
**单平台、单段失败不影响其余**，报错码怎么办照 `dby-gateway/references/protocol.md` 第 6 条。
多段里的失败在平台条目上是 `BANNED_SEGMENT_FAILED`（顶层退出码 3、`BANNED_CHECK_PARTIAL`），
它回答的是「这次只覆盖了几段」，与单平台整体失败的 `error` 一样**不能当通过**。
