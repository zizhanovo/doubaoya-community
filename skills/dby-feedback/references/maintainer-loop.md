# 反馈的消费端与措辞红线（维护者读；用户与 agent 不需要）

## 收上来的反馈往哪去（消费端）

没有消费路径的收集就是囤积——囤积正是 curl 教训的另一面（维护者时间被吃掉）。每类各有去处：

- `bug` → **进修复队列**：逐条核对「细节对得上真实记录」后按严重度排期；对不上的按 slop 处理，不进队列。
- `friction` / `idea` → **攒够同类就开一个 openspec change 提案**：本仓已有
  `proposal → specs → design → tasks` 这条工作流，反馈是它天然的输入源。单条不动手，
  同一摩擦点/诉求出现第二、三次时聚合成一个 change 的 Why。

处理完记得在回复渠道（GitHub issue / Gitee）关环：告诉反馈者结论，哪怕结论是「不做，理由如下」。

## 安装标识的措辞红线

随反馈发送的安装标识是**假名标识符**（本地随机生成、不从可识别信息派生、用户可用
`reset-id` 重置）。文档与用户可见文案**不得用「匿名」暗示它不受数据保护法规约束**——
假名化数据在 GDPR 语境下仍属个人数据。正确说法：「随机生成的安装标识，不含你的任何身份信息，
可随时重置」。
错误说法（别用）：「完全匿名，不涉及任何个人数据」。

## 端点契约（后端上线时改这里指到的配置）

接收端的路径、请求体字段名、鉴权与速率限制策略尚未与后端敲定（见 openspec change
`dby-feedback` 的 Open Questions）。当前包按统一信封（`success` / `requestId` / `data` /
`error`，`notice` 原样转达）解析响应；端点地址与字段名都在 `scripts/endpoint.json` 里，
后端定形后**只改配置发新版，不动代码**。
