# 反馈成文协议（先分类，再走各自分支）

写反馈前先判定类别，三类的提问**实质不同**，不是同一套换措辞——共用一套模板会把质量拉平到最低那类。

## 第一步：分类

- `bug`：做了某事，没得到该有的结果。
- `friction`：结果对了，但过程别扭。
- `idea`：希望这里能多做点什么。

拿不准 bug 还是 friction 就问自己一句：**最终结果对不对？** 对 = friction，不对 = bug。

## 第二步：走对应分支的自查提问

### bug 分支（问事实）

1. 按工具调用顺序，本次会话里执行了哪些操作？（逐条列，含命令与退出码）
2. 实际结果是什么？期望结果是什么？（**分开写，不许糅在一句里**）
3. 原始错误文本是什么？（可直接引用的那段，不改写）
4. 可否复现？（复现过写步骤；没复现过就写「未复现」，别猜）

### friction 分支（问当时那一刻）

这一支**不要求用户客观描述缺陷**——要的是当下的卡点，回忆会被峰终效应抹掉，所以当场问：

1. 当时想达成什么？
2. 卡在哪一个具体动作上？
3. 当时期待发生什么？
4. 落差在哪——实际发生的与期待差在哪一点？

### idea 分支（问差距）

1. 现在的做法是什么？（真实走过的路径，不是想象的）
2. 为什么不够？（具体场景里差在哪）
3. 期望的结果是什么？（描述结果，不是描述实现方案）

只写一句功能描述不算 idea 反馈——没有「现在为什么不够」，维护者无从判断值不值得做。

## 第三步：真实性拦截（写完逐条核）

**每个细节必须对应真实工具调用记录**：报告里出现的命令、文件路径、函数名、错误文本、返回值，
必须能在本次会话里真实发生过的工具调用或读取中找到出处。对不上的**删除，或标注为未核实**，
绝不以肯定语气写出。

反面教材（curl 项目实测的三个 AI slop 反模式，六年监测里纯 AI 生成的报告零命中真实漏洞）：

1. 引用代码库里不存在的函数（报 `strcpy` 溢出，而 curl 里没这个函数）；
2. 报不支持的功能的漏洞（报 WebSocket 漏洞，而当时根本不支持 WebSocket）；
3. 伪造调试记录（附完整 GDB 会话，里面引用的函数不存在）。

这三种的共同点：**细节对不上真实记录**。上面那条硬约束就是冲它们来的。

## 第四步：观察与推测分开

报告分两个层级：「我观察到的现象」与「我对原因的推测」。

- 推测写在明确标注为**推测（未核实）**的章节里，与观察到的事实分开；
- 不许把报错信息直接当作根因（报错是现象，根因要另外论证）；
- 无法判断原因时只写现象，**不编造原因**；
- **不要求给出解决方案**——把经过与可优化点讲清楚即可，方案是维护者的活。

## 第五步：取材约束（正文只许引三类素材）

报告正文只引用：① 本次会话中 agent 执行过的动作；② 观察到的错误与返回；③ 按白名单采集的机器事实。
**不引用**用户的文件内容、正在编辑的正文、上下文里的资料。约束的是取材，不是表达——章节内怎么写、
写多长、用什么措辞不受限。

- ✅ 正例：排版结果不对时写「一篇约 2000 字、含 3 个二级标题的文稿，经排版脚本处理后二级标题全部丢失」
  ——只描述现象与结构特征，正文一个字没进报告。
- ❌ 反例：把用户文稿的开头两段贴进报告「方便维护者复现」——正文进了报告就离开了用户机器，
  结构特征足够复现，原文不是必需的。

错误文本里嵌了用户内容时同理：保留错误的结构与代码，裁掉其中的用户内容片段。

## 报告骨架（固定章节 + 节内自由写）

章节名固定（保证讲清楚），节内怎么写不限（不削足适履）。`# 反馈：<一句话标题>` 起头，
首行注明分类，随后按分支取章节：

- **bug**：`## 操作序列` → `## 实际结果` → `## 期望结果` → `## 原始错误文本` → `## 可复现性` → `## 推测（未核实）`（没有就省）
- **friction**：`## 当时想达成什么` → `## 卡在哪个动作` → `## 期待是什么` → `## 落差在哪` → `## 推测（未核实）`（没有就省）
- **idea**：`## 现在的做法` → `## 为什么不够` → `## 期望的结果`

机器事实不进正文——`prepare` 会按白名单采集后随载荷附上，正文里不用重抄。
