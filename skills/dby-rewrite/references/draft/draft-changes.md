# 交付带改动清单 + 提交到稿件（可选）

> 每次改写交付都读第一节；用户要把结果存进稿件面时才读第二节。

## 1. 交付同时给成品 + 改动清单

**不只给改写后的成品，还要给一份 `changes[]`**：把「原文 → 改写后」逐处拆成一条条改动，
每条都能回答「这一处为什么这么改」。这是稿件面（`dby-api` 的 `draft submit`）能收的形状，
也逼自己把「凭感觉顺了一遍」变成「每处改动都有名字」。

**怎么拆**：不是逐字 diff，是按**读者能感知的最小单位**（一句话 / 一个短语）比较原文与改写稿；
原文这句在改写稿里找不到对应、或被换了说法，就是一条改动。纯格式调整（加 emoji、加 `#` 标签、
分段）不算改动，那是平台格式适配，不是"改了这句话"。

每条改动的形状：

```json
{"anchor": {"exact": "原文里这一句，原样摘录"},
 "replacement": "改写后对应的说法（整句删除则传空串）",
 "reason": "一句话：为什么这么改",
 "tag": "技法名或留空"}
```

- `anchor.exact` **必须是原文中逐字能找到的一段**——摘录，不要转述；改写稿里同一句话在原文出现
  不止一处时，`reason` 里顺带说清是哪一处（`draft submit` 会做本地消歧检查）。
- `reason` 落到「这条通用纪律 / 这个平台的 Workflow 第几条」，别写「更好」「更自然」这类空话。
  例：「首句改钩子——抖音黄金三秒规则」「删外站联系方式——小红书发布硬限制」。
- `tag` **从目标平台自己的 `references/<平台>.md` 里已经点名的技法词取**（如公众号的「金句」「钩子」，
  小红书的「二极管标题法」「种草口吻」，抖音的「黄金三秒」）；这条改动对应不上任何一个点名技法就留空
  （`tag: null`），**不要现造一个词**——造词等于给复盘（`dby-write` 模式 B）喂了个新分类却没人知道它是什么。

多平台一稿多发时，**每个平台各出一份自己的 `changes[]`**（锚点都指向同一份原文，互不影响）。

## 2. 提议一次：要不要提交到稿件

交付改写成品 + `changes[]` 之后，**问一次**：

> 要不要把这版改写提交到稿件（方便你逐条采纳/拒绝、留评论）？

- 用户没给稿件 id → 一并问「已有稿件还是新建一份」。
- 用户说不用 / 不回应 → 到此为止，**不主动再提第二次**（这是本包"不反问、不确认"纪律的唯一例外，
  且只问这一次）。
- 用户确认 → 才调 `dby-api` 的脚本，**写入前必须有这次确认**，不能因为"反正用户大概率想存"就替他决定。

```bash
D=~/.claude/skills/dby-api/scripts/doubaoya.mjs

# 没有稿件 id：先建稿（bodyMd 用原文，author 标明来源）
node "$D" draft create '{"title":"<标题>","bodyMd":"<原文>","author":"dby-rewrite"}'
#   → 记下返回的 draft.id 与 version.version（新建稿件是第 1 版）

# 已有稿件 id：提交这版改写（changes[] 就是第 1 节产出的清单，baseVersion 是原文所在版本号）
node "$D" draft submit <id> '{"baseVersion":<原文版本号>,"author":"dby-rewrite","changes":[...]}'
```

`submit` 会先本地预检 `changes[]`（不联网发起写请求前先核对每条锚点在 `baseVersion` 正文里能唯一定位、
互不重叠、理由齐全），预检不过会打出第几条哪里错（`ANCHOR_NOT_FOUND` 未命中 / `ANCHOR_AMBIGUOUS` 不唯一 /
`REASON_MISSING` 缺理由 / `OVERLAP` 范围重叠 / `DUPLICATE` 与前一条重复），**不改清单就重交没有意义**——
按提示改锚点或理由。提交冲突（409 `VERSION_CONFLICT`）说明有人抢先改过，重新 `draft get <id>` 拿最新
`headVersion` 再交，别对着旧 `baseVersion` 硬重试。
