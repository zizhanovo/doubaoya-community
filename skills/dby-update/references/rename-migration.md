# 改名迁移（renames.json）

> 只在**上游把某个包改了名 / 合并进另一个包**、需要把老目录里的本地数据搬到新包时读它。
> 普通的归档 / 新增 / 刷新用不到。

上游偶尔会把某个包**改名**（或合并进另一个包），而不是单纯下架。这种情况光「归档老的、装新的」
不够——用户留在老目录里的本地数据（比如 `dby-publish` 的 `config.json`）会跟着老目录
一起进归档，用户得自己手动把它挖出来搬过去。改名迁移就是为了把这一步自动化。

- **表在哪**：仓库根 `renames.json`（跟 `versions.json` / `known-hashes.json` 同一层），对账器
  每次对账都会去拉一份。里面每条是 `旧 slug → { to: 新 slug, userFiles: [...] }`。
- **`userFiles` 的语义**：老目录里**属于用户本地数据**的相对路径（文件或以 `/` 结尾的目录）。
  对账器只搬「老目录有、**上游新包没有**的文件」——比如新包自带了 16 套内置主题，老目录里那份
  同名主题**不会**覆盖它；但用户自己加的主题、自己填的 `config.json`，因为新包里没有同名文件，
  就会被搬过去。
- **执行顺序固定是「装新包 → 搬本地数据 → 老目录归档」**，且**逐条独立**：
  1. 新包先装好（正常刷新流程的一部分，不是单独一步）；
  2. 把老目录里 `userFiles` 点名、且新目录没有同名文件的那些，逐一复制过去，并读回比对确保
     逐字节相同；
  3. 只有这一条**全部搬完没出错**，老目录才会归档（归档方式、复原方式跟普通下架完全一样，
     manifest 里会写清楚是因为改名、改名去了哪个包）；`skills` 的安装记录也会一并清掉这个老 slug。
  一条改名迁移失败**不影响其他条**——脚本会继续处理下一条，最后把失败的那几条单独列出来。
- **冲突怎么处理**：如果新目录**已经有**用户数据同名的那个文件（比如新包也自带一份
  `config.json`，这不该发生但确实可能发生），对账器**不覆盖**，原样保留新目录里的那份，只在
  输出里提示「冲突未覆盖」并给出老文件现在在归档目录里的路径——**这一句要原样转述给用户**，
  由用户自己决定要不要手动合并。
- **失败怎么处理**：某一条搬运过程中出 I/O 错误（权限、磁盘满……），这一条**不会**归档老目录
  （留在原地不动，数据不会丢），脚本会打印一条可以直接手工执行的 `cp -R` 命令。**把这条命令
  原样转述给用户**，让他自己确认完再重跑一次对账。
- **受 git 跟踪的老目录同样不搬、不归档**：判据和普通下架完全一致（见上面那条红线），
  脚本会单独提示是「受跟踪」还是「git 判不出来」，处置建议也不一样，转述时别混着说。
- **幂等**：搬完一次之后老目录已经不在了，下次对账 survey 不到它，自然不会有第二次搬运
  或第二份归档——不用手动清理什么状态。

> 🔴 **为什么发布要分两趟（先发"会读表的对账器"，几天后才发"填满的表"）**：`skills add` 把
> `dby-update` 自己刷新成新版之后，**当前这次对账走的仍是旧代码**——同一个 Node 进程不会在
> 自己被更新后重启去接着跑（见 `scripts/reconcile.mjs` 文件头那段"自更新顺序"的注释）。
> 如果改名和"读表能力"同一趟发布，老用户第一次撞见改名时，实际在跑的还是**不认识
> `renames.json`** 的旧对账器——它会退化成把老目录整体归档（数据不丢，但不会自动搬家）。
> 所以要先发一趟只教会对账器"怎么读表、怎么搬"（这趟表内容是空的，行为零变化），
> 等存量用户的对账器都升级上来了，再单独发一趟把表填满去真正改名。

- **跳过第一趟机制升级、直接撞上改名的用户怎么办**：不会丢数据，只是要多一步手动。老目录会被
  整个搬进归档目录（含 `config.json` 等所有本地文件），脚本照常会打印归档路径和复原命令。
  把归档目录里对应文件（比如 `<归档路径>/config.json`）**手动复制**到新包目录下即可；
  复原命令能把整个老目录搬回原处，如果想先看一眼内容也可以用它。
