# staged 原子切换：项目 scope 的刷新/新增是怎么落盘的

3.x 之前刷新一个包 = `skills add` 在现有目录里**逐文件覆盖**。两个真实事故推动了改造：
多包更新累计文件操作数顶到宿主的批量删除防护（更新停在半路）；以及失败后留下「一半旧一半新」
的目录，能发现、不能恢复。现在项目 scope 走三段式：

1. **旁路安装**：`skills add` 是 cwd 相对的。把 cwd 指向 `<scope>/.doubaoya/staging/<事务>/install`，
   新版就整包落进 staging，**现有安装目录零读写**。staging 里产生的 `skills-lock.json` 是
   「假项目」的账本，随事务清掉，绝不覆盖项目里真正的 lock。
2. **切换前逐包校验**（任一不过就不切那个包，现有版本一个字节不动）：
   - `SKILL.md` 的 frontmatter 能被真 YAML 解析（严格子集、fail-closed：别名 `*`、锚点、tab
     缩进这类真 YAML 也报错的构造第一时间拦下）；
   - 目录内容哈希 == 索引声明的目标版本哈希（一次覆盖「下载完整吗 / 装对版本吗 / 被改过吗」）；
   - `SKILL.md` 引用的 `scripts/` 文件在场（对还没盖版本戳、比不了哈希的包也把得住）。
3. **目录级原子切换**：每个包只有两次目录移动——现有真身 `rename` 进归档、staging 里的新版
   `rename` 进真身位置。安装目录内**不发生任何单文件删除或覆盖**。`.claude/skills/<slug>` 那类
   软链原地不动（路径没变，真身换掉后它自然指向新版），缺的补建、指错的重指。
4. **切换后逐包复核**：内容哈希、每个受管目录的落位都解析到新真身、`.dby/origin.json` 在场。
   复核不过就把归档那份 `rename` 回来，该包回到更新前版本。

## 事务粒度：逐包原子，不是全有或全无

6 个包里 1 个失败：那 1 个回滚（或不切换），**另外 5 个保留新版**，退出码非 0。
所以失败后可能出现「部分包是新版、部分还是旧版」的中间态——这是**故意的**：一个坏包在上游
修好之前每次重跑都会再失败，全量回滚等于让用户永远拿不到那 5 个好的。本仓的包彼此松耦合，
版本不齐可用；输出会逐项列名（哪个成功、哪个回滚到哪版），重跑即可续上。

## 已知窗口：两次 rename 之间进程被杀

`rename(现目录 → 归档)` 与 `rename(staging → 现目录)` 之间有一个只有两次系统调用宽的窗口，
安装位置短暂不存在。进程恰好在这中间被杀（Ctrl-C、断电）会留下「这个包没了」的状态。
**不用锁文件去消除它**（复杂度不值），因为它是**可完全恢复的**：

- **归档不删除**：换下来的旧版整目录躺在 `<scope>/.doubaoya/archive/<时间戳>/`；
- 归档根里的 `manifest.json` 逐条记着每个目录原来在哪（`from`）、现在在哪（`to`）；
- 恢复 = 把那条的 `to` 移回 `from`（`mv <to> <from>`），或跑脚本打印过的整份复原命令。

重跑一次 `/dby-update` 也会把缺的包当「新增」补齐到当前版。

## 回滚失败时

把归档那份移回来本身也可能挂（权限、磁盘满）。这时输出会带三样东西，一样不少：
归档目录的**绝对路径**、**可直接粘贴的手动复原命令**、以及**原始错误**。按命令手动移回即可。

## 全局 scope（`-g`）没有这层保证

`skills add -g` 走固定的家目录路径、不吃 cwd，旁路这招无效。全局 scope 维持原地覆盖安装：
**不提供原子切换与自动回滚，失败可能留下半更新**。输出里两个 scope 的保证级别会分别说明。
要事务保证，用项目 scope 安装。

## 其他要点

- **同卷硬要求**：目录级 `rename` 跨文件系统会抛 `EXDEV`。staging 落在 `<scope>/.doubaoya/` 下
  正是为了与安装目录同卷；真撞上跨卷（比如 `.doubaoya` 被软链去了别的卷）会**报错停手**，
  绝不退化成逐文件拷贝——那会把本方案要解决的问题原样带回来。
- **磁盘峰值**：事务期间 staging 里的新版与现有版本同时在盘，峰值占用约翻倍（单包几百 KB 量级，
  全集也就几 MB）；磁盘紧张的机器可能在旁路安装那步失败——失败时已安装的包一个字节没动。
- **staging 无论成败都会清理**；成功跑完不存在任何残留的 staging 目录。
- **`skills-lock.json` 与外部工具**：旁路安装对 `npx skills list` / `experimental_install`
  应当不可见——某包**切换成功并复核通过后**，skills CLI 在 staging 里生成的该 slug 账本条目会
  合并进项目根的 `skills-lock.json`（保持文件原有键序与缩进）。三条边界：失败/回滚的包**不**
  写入（账本只反映真实落地的东西，那几个 slug 保持旧记录）；项目根没有这本账（从没用 CLI 装过）
  不凭空创建；归档/下架仍由 `skills remove` 清记录。
- **dby-update 自己最后切**：事务开始时先把正在跑的这份脚本连同 references/ 复制进事务目录；
  它排在切换序列末位，切换自身之后本进程不再读安装路径下的任何文件——所以那一轮会跳过
  收尾核对（lock 重建、联网自检），并提示再跑一次 `/dby-update` 由新版补齐。
