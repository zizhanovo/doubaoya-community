# dby-update：把本鸭对账到最新

用户已明确要求更新都爆鸭（本鸭）。直接执行，不再做第二次文字确认；宿主若要 Shell 权限，由用户在宿主权限窗口里决定。

## 这个 skill 干的是「对账」，不是「更新」

让本机这套本鸭 skill **等于**上游当前全集：

- **归档**上游已经下架的（否则它们会永久停在被砍前的旧契约上，调用必然报错）
- **装上**新增的
- **刷新**内容哈希落后于上游当前版的，**以及内容虽是当前版、但少了一处落位的**；两者都不缺的一个都不动

> 🔴 **「内容是当前版」不等于「已经就位」。** 宿主是按**自己那个目录**读 skill 的——Claude Code 只读
> `.claude/skills`。一个包只落进了 `.agents/skills` 时，它内容再新，在 Claude Code 眼里也**根本不存在**。
> 所以对账的判据是「内容 **且** 落位」：本机任一受管安装目录缺落位，这个包就照样重装一遍补齐，
> 计划里会用 🩹 单列出来说明原因。转述时别把它说成「白重下了」——那正是在补一个用户看不见的窟窿。

> 所以「本机已经和上游一致」时，它的结论就是**无需任何操作**——一个包都不会重下。
> 真想把某个包重装一遍（比如文件坏了），用 `--force-refresh` 全量重下。

> ⚠️ 别用 `npx skills update`：它只更新「已经装了的」，**永远删不掉上游已下架的那些**。
> 老用户机器上常见几十个早就砍掉的平台垂类 skill，`update` 一辈子摸不到它们。

### 怎么判断「这包是不是本鸭发的」

**判据是 slug × 内容哈希这一对，不看它当初是从哪个源装的。** 上游 `known-hashes.json` 是一份闭集，
记着本鸭发布过的每一个 slug 的每一版内容哈希；先拿目录名索到那一栏，再比内容哈希。于是有三态：

| 状态 | 判据 | 处置 |
| --- | --- | --- |
| 当前版 | 哈希 = 上游当前版 | 保留，**不刷新**（除非 `--force-refresh`） |
| 我们的旧版 | 哈希命中闭集里某个历史版 | 可归档、可替换 |
| **你动过手** | slug 是本鸭的，但哈希谁都不命中 | 🔴 **跳过并列进报告，一个字都不动**，连刷新都不给（刷新会盖掉你的改动） |
| 别人家的 | slug 根本不在闭集里 | 不碰 |

这样改名（本仓早期叫 `redfox-community`）、`source` 字段缺失、别家有同名包，都不会判错。

### 删除一律做成「归档」

要下架的包**移进 `<scope>/.doubaoya/archive/<时间戳>/`，不做 `rm`**，同目录留一份 `manifest.json`
写明每个包原来在哪、怎么移回去。多一个目录的成本，换「删错了还能捞回来」。

三件配套的事，**转述结果时都要带上**：

- **怎么捞回来**：脚本在归档后会直接打印一条可复制粘贴的复原命令（读 manifest 逐条移回原处）。
  原样转给用户，别只说「见 manifest」。移回去 skill 立刻能用（宿主按目录读），只是
  `npx skills list` 的安装记录已被清掉，想让 CLI 也认回来就重装一次。
- **归档目录对 git 隐形**：归档根落在用户自己的项目仓里，所以脚本会在 `.doubaoya/.gitignore`
  写一个 `*` 自忽略整个目录（用户已有该文件就不动）。**不改用户的 `.gitignore`。**
- 🔴 **受 git 跟踪的包一律不归档**：如果某个上游已下架的包在用户仓库里是被 git 跟踪的
  （把 skill 版本化进仓库是真实存在的用法），归档就等于从人家工作区里删受跟踪文件。
  脚本会跳过它们、单列一栏点名说明——**这一栏必须原样转述给用户**，由用户自己决定怎么处理。

## 改名迁移（renames.json）

上游偶尔会把某个包**改名**（或合并进另一个包），而不是单纯下架。这种情况光「归档老的、装新的」
不够——用户留在老目录里的本地数据（比如 `dby-publish` 的 `config.json`）会跟着老目录
一起进归档，用户得自己手动把它挖出来搬过去。改名迁移就是为了把这一步自动化。

- **表在哪**：仓库根 `renames.json`（跟 `versions.json` / `known-hashes.json` 同一层），对账器
  每次对账都会去拉一份。里面每条是 `旧 slug → { to: 新 slug, userFiles: [...] }`。
- **`userFiles` 的语义**：老目录里**属于用户本地数据**的相对路径（文件或以 `/` 结尾的目录）。
  对账器只搬「老目录有、**上游新包没有**的文件」——比如新包自带了 16 套内置主题，老目录里那份
  同名主题**不会**覆盖它；但用户自己加的主题、自己填的 `config.json`，因为新包里没有同名文件，
  就会被搬过去。
- **执行顺序固定是「装新包 → 搬本地数据 → 老目录归档」**，且**逐条独立**：
  1. 新包先装好（正常刷新流程的一部分，不是单独一步）；
  2. 把老目录里 `userFiles` 点名、且新目录没有同名文件的那些，逐一复制过去，并读回比对确保
     逐字节相同；
  3. 只有这一条**全部搬完没出错**，老目录才会归档（归档方式、复原方式跟普通下架完全一样，
     manifest 里会写清楚是因为改名、改名去了哪个包）；`skills` 的安装记录也会一并清掉这个老 slug。
  一条改名迁移失败**不影响其他条**——脚本会继续处理下一条，最后把失败的那几条单独列出来。
- **冲突怎么处理**：如果新目录**已经有**用户数据同名的那个文件（比如新包也自带一份
  `config.json`，这不该发生但确实可能发生），对账器**不覆盖**，原样保留新目录里的那份，只在
  输出里提示「冲突未覆盖」并给出老文件现在在归档目录里的路径——**这一句要原样转述给用户**，
  由用户自己决定要不要手动合并。
- **失败怎么处理**：某一条搬运过程中出 I/O 错误（权限、磁盘满……），这一条**不会**归档老目录
  （留在原地不动，数据不会丢），脚本会打印一条可以直接手工执行的 `cp -R` 命令。**把这条命令
  原样转述给用户**，让他自己确认完再重跑一次对账。
- **受 git 跟踪的老目录同样不搬、不归档**：判据和普通下架完全一致（见上面那条红线），
  脚本会单独提示是「受跟踪」还是「git 判不出来」，处置建议也不一样，转述时别混着说。
- **幂等**：搬完一次之后老目录已经不在了，下次对账 survey 不到它，自然不会有第二次搬运
  或第二份归档——不用手动清理什么状态。

> 🔴 **为什么发布要分两趟（先发"会读表的对账器"，几天后才发"填满的表"）**：`skills add` 把
> `dby-update` 自己刷新成新版之后，**当前这次对账走的仍是旧代码**——同一个 Node 进程不会在
> 自己被更新后重启去接着跑（见 `scripts/reconcile.mjs` 文件头那段"自更新顺序"的注释）。
> 如果改名和"读表能力"同一趟发布，老用户第一次撞见改名时，实际在跑的还是**不认识
> `renames.json`** 的旧对账器——它会退化成把老目录整体归档（数据不丢，但不会自动搬家）。
> 所以要先发一趟只教会对账器"怎么读表、怎么搬"（这趟表内容是空的，行为零变化），
> 等存量用户的对账器都升级上来了，再单独发一趟把表填满去真正改名。

- **跳过第一趟机制升级、直接撞上改名的用户怎么办**：不会丢数据，只是要多一步手动。老目录会被
  整个搬进归档目录（含 `config.json` 等所有本地文件），脚本照常会打印归档路径和复原命令。
  把归档目录里对应文件（比如 `<归档路径>/config.json`）**手动复制**到新包目录下即可；
  复原命令能把整个老目录搬回原处，如果想先看一眼内容也可以用它。

## 执行步骤

### 1. 找到对账脚本

按顺序找第一个存在的：

```
~/.claude/skills/dby-update/scripts/reconcile.mjs
~/.agents/skills/dby-update/scripts/reconcile.mjs
./.claude/skills/dby-update/scripts/reconcile.mjs
./.agents/skills/dby-update/scripts/reconcile.mjs
```

**找不到**说明本机装的是旧版 dby-update（还没有对账能力）。先跑一次下面这条把自己升级上来，然后**重新找一遍**：

```bash
npx -y skills add zizhanovo/doubaoya-community -g -s '*' -a claude-code universal -y
```

🔴 **找到了、跑了、却一个字都没打印（退出码 0、零字节）**：不是「没事可做」，是**本机装的是旧版**。
上面这张表里 `.claude/skills/…` 那两条通常是**软链**（真目录在 `.agents/skills/…`），而旧版的入口
守卫经软链调用时整个脚本一步都不跑。**先换 `.agents` 那条真路径重跑一次**（能出东西就说明是这个病），
再用上面那条命令把自己升级上来，然后重新找一遍路径。

### 2. 先看清单（🔴 显式给 scope，别靠 auto 猜）

```bash
node <上一步找到的路径> --dry-run --scope global              # 当初带 -g 装的（最常见）
node <上一步找到的路径> --dry-run --scope project --project-dir <项目目录>
```

**为什么必须显式给**：`--scope auto` 是按**当前工作目录**猜的。cwd 选错时，目标 scope 里
一个本鸭包都没有 ⇒ 计划静默变成「整仓新增 N 个、归档 0 个」——凭空多出一整套副本，
而真正该清的死包一个没清，而且这份计划长得**完全正常**。脚本现在会对这种情况打一行 ⚠️
警告，看到就停下来先确认 scope，别直接执行。

不确定装在哪，就两个都看一眼（`--scope global` 一次、`--scope project --project-dir <目录>` 一次）。

它会联网取上游全集与历史闭集，然后打印**要归档哪些、要装哪些、要刷新几个、以及哪些因为你动过手而不碰**，
这一步一个字都不会改。把这份清单**原样转述给用户**——尤其是「要归档」那几个的名字，
以及「你改过的」那几个（那是在告诉用户：这些我认出来你动过，所以不动它们）。

### 3. 确认后执行

用户看过清单、认可了，再跑（**scope 参数和上一步给的保持一致**）：

```bash
node <路径> --yes --scope <上一步用的那个> [--project-dir <目录>]
```

脚本会自己完成：归档 → 拉齐全集 → 复核 → 自检（skill 有没有落盘、`DOUBAOYA_API_KEY` 在不在、
doubaoya.com 连不连得通），最后打印一份结果，并告诉用户归档放在哪。

**退出码**：`0` 全通过；`3` 对账做完了但自检有项没过；`1` 用户取消；`2` 需要确认但当前不是交互终端；`4` 出错。

> 📝 **项目里的 `skills-lock.json` 会被一起改，这是预期的。** 它是 skills CLI 记「装了哪些包、哪个版本」
> 的文件，而且**受 git 跟踪**（不像 `.doubaoya` 自带忽略），所以对账跑完 `git status` 会多出这一行。
> 脚本也会在结尾提一句。转述时主动说明它是预期改动、照常提交即可，别让用户以为工具弄脏了工作区。

> ⚠️ **跑挂在「拉取上游」这一步 = 半迁移态**（实测最常撞上 github clone 网络抖动）：归档已经落盘、
> 要拉的那批一个没落，磁盘**被改了一半**。脚本会在报错里说清已经归档了几个、以及**重跑同一条命令
> 即可续上（归档不会重复执行）**——把这几句原样转述给用户，然后就是**直接重跑**，不需要任何手工收拾。

### 4. 转述结果

- 全通过 → 告诉用户归档了几个、装了几个、现在共几个、归档目录在哪、**怎么把归档捞回来**
  （把脚本打的那条复原命令原样贴给用户），并提醒**新建一次对话**才能读到新能力。
  如果有「你改过的」「受 git 跟踪所以没动的」「git 判不出来所以跳过的」这几类，**必须各单独说一句**，
  别让用户以为它们被漏掉了。🔴 后两类别混着说：前者是「这是你自己版本化的包，要清你自己 `git rm`」，
  后者是「这台机器上的 git 没能回答我，你先修好 git 再重跑」——用户该做的事完全不同。
- 有 🩹「缺落位」那一栏 → 说清这几个包**内容本来就是最新的，重装是为了把缺的那处安装目录补上**
  （少一处 = 那个宿主根本看不见它）。别说成「白重下」。
- 本机已经和上游一致 → 脚本会直接说「无需任何操作」，**照实转述**，别自己补一句「已刷新 N 个」。
- 自检有 ❌ → **明确说卡在哪一步**（是 skill 没落盘、还是没配钥匙、还是连不上服务），把脚本给的那句处理建议一起带上。别笼统说「失败了」。

## 常用参数

| 参数 | 作用 |
| --- | --- |
| `--dry-run` | 只看清单，绝不执行 |
| `--yes` | 跳过确认直接执行（**只在用户已经看过清单之后用**） |
| `--force-refresh` | 连「已经是当前版**且落位齐全**」的包也重下一遍。默认只刷新落后的和缺落位的；这个旗标留给「我这个包坏了想重装」 |
| `--verbose` | 连「别人家的」和「你改过的」一起列名字 |
| `--scope auto\|global\|project` | 🔴 **每次都显式给**。默认 `auto` 是按 cwd 猜的，猜错会静默变成「整仓重装」。当初带 `-g` 装的就是 `global` |
| `--project-dir <目录>` | 项目级安装在别的目录时指定 |
| `--json` | 机器可读输出 |
| `--self-check` | 离线自检脚本自身（不联网） |

## 边界

- **只碰本鸭发过的包**，判据是上面那张三态表（内容哈希命中闭集）。
  **别人家的、以及你自己动过手的，一个字都不动。**
- **要下架的包是移进归档目录，不是删掉**，随时能按 `manifest.json` 移回来；归档目录自带
  `.gitignore` 对 git 隐形，不会污染用户仓库。
- 🔴 **受 git 跟踪的包一个都不归档**；git 探测跑不通、判不出来的，同样保守跳过，宁可少归档一个。
  两种情形脚本会**分两栏**打出来，因为处置不同（自己 `git rm` vs 先修 git）。
- **不动你的本地数据 / 配置**：`dby-publish` 的 `config.json`、`dby-charter` 的创作 DNA、
  封面 / 草稿等产出文件都不受影响——对账只覆盖 skill 目录里受版本管理的那些文件。
- 不创建后台任务、定时任务或 Agent Hook。
- 用户只问「有什么更新 / 现在什么版本 / 要不要更」→ **先回答，不执行**（`--dry-run` 正好用来回答这个）。
  明确要实际同步时才跑第 3 步。
- 只想更新某一个 skill：`npx -y skills update <skill 名> -g`，只碰点名那个（但它不会做对账）。
